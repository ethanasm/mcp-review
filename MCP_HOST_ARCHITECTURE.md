# MCP Host Architecture

## Overview

`mcp-git-reviewer` is an **MCP host** application. It has an orchestration layer that manages the full lifecycle of multiple MCP tool servers and coordinates an LLM conversation across them.

This document describes the host architecture: how it orchestrates tools, manages the conversation loop, handles multi-model inference, and ensures reliable operation. For the rationale behind choosing MCP host over a monolithic approach, see [ADR-001](docs/adr/001-mcp-host-architecture.md). For the multi-model and conversation loop decisions, see [ADR-002](docs/adr/002-multi-model-gather-analyze.md).

## Component Breakdown

### Tool Registry (`src/host/tool-registry.ts`)

Maps tool names to their MCP server instances. When the LLM requests a tool call, the registry routes it to the correct server process.

**Responsibilities:**
- Maintain a mapping of `toolName → serverProcess`
- Register tools during server capability negotiation at startup
- Route tool call requests to the appropriate server
- Return structured results back to the conversation manager

**Tool Servers:**

| Server | Tools | Purpose |
|--------|-------|---------|
| Git Diff | `get_diff`, `get_diff_stats`, `get_commit_messages`, `get_blame` | Surface what changed and why |
| File Context | `read_file`, `read_lines`, `list_directory` | Provide surrounding code context |
| Convention Scanner | `scan_lint_config`, `find_similar_patterns`, `get_project_conventions` | Understand project-specific patterns |
| Related Files | `find_importers`, `find_exports`, `find_test_files`, `find_type_references` | Trace the dependency graph |

Each server is a separate process communicating via MCP stdio transport. Adding a new tool server requires zero changes to the host or existing servers.

### Provider Abstraction (`src/llm/provider.ts`)

Abstracts over multiple LLM providers, enabling the multi-model strategy where a fast/cheap model gathers context and a quality model produces the final review.

```typescript
interface LLMProvider {
  call(params: {
    model: string;
    max_tokens: number;
    system: string;
    tools?: ToolDefinition[];
    messages: LLMMessage[];
  }): Promise<LLMResponse>;
}

interface ModelConfig {
  gatherModel: string;    // e.g., 'qwen3-coder' (Qwen3-Coder via OpenAI-compatible API)
  analysisModel: string;  // e.g., 'claude-haiku-4-5'
}
```

The provider normalizes message formats between providers. This is important because the analysis model receives a conversation history that was generated by a different model during gathering. See [ADR-002](docs/adr/002-multi-model-gather-analyze.md) for why we flatten messages at the handoff point rather than passing raw history.

### Conversation Manager (`src/host/conversation.ts`)

The core orchestration layer. Manages the two-phase review process: context gathering and analysis.

## Conversation Flow: Gather → Analyze

The conversation follows a two-phase design where context gathering and review analysis are handled by separate models optimized for each task.

### Phase 1: Preloading

Before the conversation loop begins, the host pre-loads predictable context to eliminate the most common first tool-call round:

- **Changed file contents** — full text of files in the diff (up to 10KB each, max configurable via `max_files`)
- **Diff truncation** — if the diff exceeds ~100K tokens, truncate to complete per-file sections with a note listing omitted files
- Skip preloading entirely when the diff is already large to stay within context limits

This is the single biggest performance optimization. It eliminates a full round-trip that the gather model would otherwise spend on "read me all the changed files."

### Phase 2: Context Gathering (ReAct Loop)

The gather model runs a ReAct-style loop: reason about what context is needed, request tools, observe results, repeat.

```
┌─────────────────────────────────────────────────────┐
│                  GATHER PHASE                        │
│                                                      │
│  Model: gatherModel (fast/cheap, e.g., Qwen3-Coder)      │
│  System prompt: gather-only, do NOT write the review │
│                                                      │
│  ┌──────────────────────────────────────────────┐    │
│  │  Round 1                                      │    │
│  │  Thought: "Need to check conventions for..."  │    │
│  │  Action:  scan_lint_config, find_importers    │    │
│  │  Observe: [tool results]                      │    │
│  └──────────────────────────────────────────────┘    │
│                      │                               │
│                      ▼                               │
│  ┌──────────────────────────────────────────────┐    │
│  │  Round 2                                      │    │
│  │  Thought: "Found pattern violation, need..."  │    │
│  │  Action:  find_similar_patterns               │    │
│  │  Observe: [tool results]                      │    │
│  └──────────────────────────────────────────────┘    │
│                      │                               │
│                      ▼                               │
│  ┌──────────────────────────────────────────────┐    │
│  │  Semantic Termination                         │    │
│  │  <gather_complete>                            │    │
│  │  Summary of gathered context and rationale    │    │
│  │  </gather_complete>                           │    │
│  └──────────────────────────────────────────────┘    │
│                                                      │
└─────────────────────────────────────────────────────┘
```

**Termination conditions (in priority order):**

1. **Semantic termination** — the gather model emits `<gather_complete>` indicating it has sufficient context. This is the expected exit path.
2. **Implicit completion** — the gather model returns `end_turn` without requesting tools or signaling completion.
3. **Safety ceiling** — `MAX_TOOL_ROUNDS` (default: 5) is reached. The loop exits and proceeds to analysis with whatever context has been gathered. A warning is logged.

**Reasoning trace:**

Each round captures a structured trace entry for debugging and observability:

```typescript
interface AgentTurn {
  round: number;
  thought: string;       // text blocks from gather model (best-effort)
  toolsCalled: string[];  // tool names invoked
  timestamp: number;
  durationMs: number;
}
```

Thoughts are extracted from text blocks that the LLM emits alongside tool_use blocks. This is best-effort — not all models emit reasoning text during tool calls. The system prompt includes a nudge ("Before each tool request, briefly state what you're looking for and why") which most models comply with regardless of architecture.

Traces are surfaced via `--verbose` mode and logged via the `debug()` utility for post-hoc debugging.

### Phase 3: Analysis Handoff

When gathering completes, the host hands off to the analysis model. The key design decision is **flattening the conversation history** at this boundary:

```typescript
function buildAnalysisPrompt(
  diff: string,
  messages: LLMMessage[],
  gatherSummary: string
): string {
  // Extract all successful tool results
  const toolResults = messages
    .flatMap(m => Array.isArray(m.content) ? m.content : [])
    .filter(b => b.type === 'tool_result' && !b.is_error)
    .map(b => b.content)
    .join('\n\n---\n\n');

  return `Review the following code changes with the gathered context.

## Diff
\`\`\`diff
${diff}
\`\`\`

## Context Summary
${gatherSummary}

## Gathered Context
${toolResults}

Provide your structured review as JSON.`;
}
```

**Why flatten instead of passing raw history:**
- The analysis model didn't generate the gather model's assistant messages — passing them as-is creates a foreign conversation history
- Tool call/result formats vary between providers (Qwen vs. DeepSeek vs. Claude)
- Flattening makes the two models completely decoupled — different providers, different prompt formats, no cross-contamination
- Enables testing by snapshotting the flattened prompt and running different analysis models against the same gathered context

The analysis model receives a clean prompt with the diff, the gather summary, and all tool results as context. It produces the final structured review output.

## Error Handling

### Tool Call Failures

Tool calls use `Promise.allSettled` rather than `Promise.all`, so one failing tool doesn't kill the entire round. Failed tools return error messages as tool results, allowing the gather model to reason about the failure and decide whether to retry, skip, or work with partial context.

```typescript
const settled = await Promise.allSettled(
  toolUseBlocks.map(block => toolRegistry.callTool({
    name: block.name,
    arguments: block.input,
  }))
);

const toolResults = settled.map((s, i) => ({
  type: 'tool_result' as const,
  tool_use_id: toolUseBlocks[i].id,
  content: s.status === 'fulfilled'
    ? s.value.content
    : `Tool error: ${s.reason?.message ?? 'unknown error'}`,
  is_error: s.status === 'rejected',
}));
```

### Safety Guardrails

| Guardrail | Mechanism | Purpose |
|-----------|-----------|---------|
| Max tool rounds | `MAX_TOOL_ROUNDS = 5` | Prevent infinite gathering loops |
| Diff truncation | `MAX_DIFF_TOKENS = 100_000` | Stay within context window limits |
| File size cap | `MAX_FILE_SIZE = 10_000` chars | Prevent single large files from dominating context |
| Max files preloaded | `max_files` config | Control preloading scope |
| Token budget tracking | `createUsageTracker()` | Monitor and report total token consumption |

## Performance Considerations

### Where Time Goes

The dominant cost is LLM inference time, which scales with input token count. Each round appends tool results to the message history, so later rounds process significantly more tokens. Even with hosted API endpoints (e.g., Qwen3-Coder via OpenAI-compatible API), the growing context per round compounds latency significantly.

```
Round 1: ~20K tokens input  →  ~3s (gather model)
Round 2: ~50K tokens input  →  ~6s (gather model)
Round 3: ~80K tokens input  →  ~10s (gather model)
Analysis: ~80K tokens input →  ~8s (analysis model)
```

### Mitigation Strategies

1. **Two-model strategy** — Use a fast, cheap model (or free, like Qwen3-Coder) for gathering rounds where quality demands are lower. The analysis model only runs once.
2. **Aggressive preloading** — Eliminate predictable first-round tool calls by pre-loading changed file contents, conventions, and lint config in the initial prompt.
3. **Tool response size caps** — Limit individual tool responses at the source (e.g., `find_similar_patterns` returns top 5 matches, not 20).
4. **Parallel tool execution** — All tool calls within a round execute via `Promise.allSettled` concurrently.

### What We Don't Do

**We do not compress tool results between rounds.** Compressing with an LLM call adds latency and cost to reduce latency and cost — the math doesn't work. Compressing with heuristics risks cutting context the analysis model needs. The right place to control context size is at the tool level (cap response sizes at the source), not post-hoc.

## Observability

### Debug Logging

All components log through a unified `debug(category, message)` utility with categories: `review`, `llm`, `tools`, `agent`, `git`.

```bash
# Enable verbose output
mcp-review HEAD~1..HEAD --verbose

# Output includes:
#   💭 Agent thought: "Need to check if this function is called elsewhere..."
#   🔧 Executing 2 tool call(s): find_importers, read_file
#   ⏱  API call #2: 4.2s, 48K input tokens
#   ✅ Gather complete after 3 rounds
```

### Usage Tracking

Token usage is tracked per-round and per-model, reported at the end of each review:

```
Token usage: 142K input / 3.2K output
  Gather (qwen3-coder): 3 rounds, 112K in / 1.8K out (free)
  Analysis (claude-haiku-4-5): 1 call, 80K in / 1.4K out (~$0.09)
  Total estimated cost: ~$0.09
```

## Configuration

Model configuration is exposed through CLI flags and the `.mcp-review.yml` config file:

```yaml
# .mcp-review.yml
models:
  gather: qwen3-coder
  analysis: claude-haiku-4-5

# Override via CLI:
# mcp-review HEAD~1 --gather-model deepseek-chat --analysis-model claude-sonnet-4-5
```

This allows users to choose their own cost/quality tradeoff. The defaults prioritize free gathering with quality analysis. If Qwen3-Coder's tool-call quality proves insufficient, switching to DeepSeek V3.2 is a one-line config change. Similarly, upgrading analysis from Haiku to Sonnet is straightforward if review quality needs improvement.
